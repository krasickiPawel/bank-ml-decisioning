# MLflow — How to use it in this demo

This project uses MLflow for:
- storing runs (params, metrics),
- storing artifacts (plots, CSVs, schema files),
- storing the trained model pipeline.

## Tracking server
The API expects an MLflow tracking server, typically:
- `MLFLOW_TRACKING_URI=http://localhost:5050`

You can open the UI in a browser:
- http://localhost:5050

## How runs are selected
The API loads a model using one of these strategies (highest priority wins):

1) Explicit model registry (if configured):
   - `MODEL_NAME=...` and optionally `MODEL_STAGE=Production` or alias.
   - This is the “production style” setup.

2) Explicit run id:
   - `MODEL_RUN_ID=...`
   - Useful for pinning a specific run.

3) `best_model.json` in the repo:
   - generated by `src/scripts/select_best_model.py`
   - This is the most demo-friendly approach:
     you can train multiple runs and pick a winner without touching registry.

4) Fallback:
   - latest runnable run in the experiment (if implemented in the loader).

## Finding a run in the MLflow UI by run id
MLflow UI is not great at “search by run_id” directly from the runs table.
The practical workaround:
- Build the URL with experiment id + run id:
  `http://localhost:5050/#/experiments/{experiment_id}/runs/{run_id}`

You can get experiment id for a run in code:
- `experiment_id = client.get_run(run_id).info.experiment_id`

The API `/health` can expose a direct `run_url` so you can click it from Streamlit.

## Artifacts this demo relies on
Some endpoints/features depend on these artifacts:

- `expected_columns.json`
  Used by `/schema` to tell clients what input columns exist.

- `example_payload.json` (optional)
  Nice for demo; pre-fills a request payload.

- `drift_reference_train.csv`
  Used by `/metrics/drift` as the baseline distribution.
  If a run was trained before this was logged, drift will return a friendly error.

- `feature_importance_top.csv`, `perm_importance_top30.csv`, `threshold_cost_table_val.csv`
  Not required for core inference. Great for demo explanations and RAG.

## Registry vs best_model.json
Registry is closer to enterprise workflows (promotion, approvals, gating).
best_model.json is faster for demo and experiments, because:
- you can update selection logic in one script,
- switching models is a file update + `/reload`,
- no UI clicking required.
